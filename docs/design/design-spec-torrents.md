# Спецификация размеров — путь просмотра через TorrServer (экраны 33–40)

> Снято 2026-09-15. Источник: `design/Lumen Torrents for Lampa - FHD.dc.html` (1920×1080, главный для кода) — сверен построчно с `- 2K.dc.html` (2560×1440) и `- 4K.dc.html` (3840×2160): все 8 артбордов присутствуют в трёх файлах в одинаковом порядке, с идентичной разметкой и размерами, отличающимися строго в 1× / 1.333× / 2×  (спот-проверка: панель Select 672→896→1344px, заголовок 28→37.3→56px). Расхождений между разрешениями не найдено.
>
> **Правило единиц: 1em = 22.811px при 1920 px** (база самой Lampa, план `2026-09-15-lumen-phase1b-torrents.md` §0.2) — **не 16**, в отличие от исходной конвенции `design-spec-card.md`. Все em ниже = px(FHD) ÷ 22.811. px(4K) = px(FHD) × 2 везде, где не оговорено иное.
>
> Бриф: `docs/design/claude-design-brief-torrents.md`. Нативные замеры/классы Lampa: `docs/research/API_NOTES_6_torrents_visual.md` (и точечно `API_NOTES_5_torrents.md` там, где потребовалось подтвердить происхождение класса). Обозначения статуса: **✓ выполнено**, **~ частично**, **✗ нет**.
>
> **Вне области замеров**: фон-подложка каждого артборда (постер/бэкдроп «Дюны», мок топ-бар «LAMPA 18:40», текст-кнопки «Смотреть»/иконка-кнопка под панелью на экране 33, кадр на экране 40 «за вуалью») — это контекст «что происходит на экране позади компонента», а не часть Select/Modal/media-loading. Он уже покрыт CSS карточки/главной (фазы 1 и 2) и не входит в Task 32.

## 11. Решения дизайна, уточняющие Task 31–33

**11.1 Экраны 35 и 36 — «документационная» компоновка, не буквальная ширина/высота.** На экране 35 три состояния Select нарисованы узкими панелями по 570px рядом, чтобы поместить сравнение на одном канвасе — это НЕ новая ширина панели: реальный `.selectbox__content` всегда 672px FHD (35%), как на экране 33. Аналогично на экране 36 оба состояния модалки сжаты по высоте (350px и «остальное»), хотя в реальном UI оба — полноэкранные. Executor должен ориентироваться на **672px** для Select во всех случаях и на **центрированную модалку** без внешних ограничений высоты для Modal. Это самая большая ловушка при поверхностном чтении экспорта.

**11.2 Иконка «назад» на экране 34 — не `chevronR` и не третья новая иконка.** Путь `M15 6l-6 6 6 6` — зеркальное отражение существующего `chevronR` (`M9 6l6 6-6 6`). Бриф прямо запрещает вводить новые иконки сверх `search`/`check`. Рекомендация для Task 32: использовать маску `chevronR` с `transform: scaleX(-1)` (или `-webkit-mask` + `scale(-1,1)`) на кнопке «назад» `.torrent-filter .filter--back`/аналогичной, а не рисовать новый путь.

**11.3 Padding строки Select не идентичен между экранами 33 (14px/16px) и 35 (11px/12px).** Бриф требует «универсальную оболочку» (раздел 1, раздел 4 п.2) — расхождение в плотности между «источником» (4 пункта) и «фильтром» (10 пунктов) можно трактовать как обоснованную адаптацию под длину списка, но численно это два разных значения. Решение для Task 32: выбрать один токен паддинга `.selectbox-item` (рекомендация — 14/16px FHD, как на «опорном» экране 33, поскольку `.selectbox` — общий компонент и его канонический вид задаёт первый показанный экран) и проверить читаемость длинного списка фильтра с этим паддингом вживую на Task 32 Step 3.

**11.4 «Приглушённый» текст в макете нигде не мельче 20px FHD (40px@4K) — бриф локально предлагал 32px@4K (16px FHD), но это ниже чек-листового минимума (раздел 6, п.3: «не мельче 40px в 4K»).** Экспорт последовательно (27 вхождений, 0 исключений в Lumen-стилизованном контенте) выбирает 20px FHD для всех мета-строк/подписей/пояснений, где бриф в разделе 3 указывал «32px» — то есть дизайнер корректно разрешил внутреннее противоречие брифа в пользу более строгого общего правила чек-листа. **Единственное реальное исключение** — подпись «Назад — отменить» на экране 40 (14px FHD/28px@4K), и оно прямо задокументировано брифом как единственное. Для Task 32 это значит: везде, где план или бриф цитируют «32px@4K» для второстепенного текста на пути TorrServer, реальное целевое значение — **20px FHD / .877em**, не 16px/.701em.

**11.5 Три состояния чек-листа — точные классы, не просто три цвета.** По `API_NOTES_5_torrents.md` (строки 443–444): нативно `li.wait{color:#fff}` (текущий И пройденные), `li.check{text-decoration:line-through}` (полностью пройденные, класс добавляется ДОПОЛНИТЕЛЬНО к `.wait`). Дизайн перекрашивает это в три визуально различных состояния: будущий шаг — `li` без классов, smoke `#7A6A5A`, без декораций; текущий — `li.wait` (без `.check`), text `#F3EDE4`, 600, крупнее (22px vs 20px); пройденный — `li.wait.check` (оба класса), `#3E3226` (темнее smoke) + line-through. Для Task 32 CSS: писать правила именно на комбинацию классов `li`, `li.wait:not(.check)`, `li.wait.check`, а не гадать по одному только `.wait`.

**11.6 `.torrnet-folder-name` в макете — JetBrains Mono, бриф требовал Golos Text.** На обоих экранах, где встречается этот элемент (38 и 39), реально нарисован `font:400 20px/1 'JetBrains Mono',monospace;color:#A89A8A;opacity:.5` — при этом бриф раздела 3 (строки экранов 38/39) явно указывает «Golos 400, 32px». Поскольку это не изолированная опечатка, а одинаковое воспроизведение на обоих экранах, вероятно осознанный выбор (имя папки — техническое имя раздачи, похоже на остальные моно-тексты рядом). Рекомендация: взять фактическое значение экспорта (Mono, 20px FHD/.877em, opacity .5) как источник истины для Task 32 — экспорт по вводным задания является «главным для кода», а расхождение с прозой брифа зафиксировать здесь как решённое.

**11.7 Инконсистентность токена фокуса кнопки: «Далее» (экран 37) ≠ «Уточнить» (экран 34).** Обе — `.simple-button` во фокусе, обе используют заливку accent + кольцо, но «Далее» полностью повторяет токен «Кнопка» брифа 1 (height 72px, scale 1.06, `box-shadow` glow), а «Уточнить» на экране 34 — заливка + кольцо без scale и без glow (упрощённый вариант). Для Task 32 требуется решение: либо унифицировать все `.simple-button.focus` на полный токен (рекомендуется, для визуальной целостности), либо явно завести «облегчённый» вариант для инлайн-кнопок внутри мини-карточек. Чек-лист брифа (п.10 «фокус везде заливка/кольцо») формально выполнен в обоих случаях.

## 12. Добавлено сверх Lampa (инвариант «только CSS»)

Проверено по `API_NOTES_5_torrents.md`/`API_NOTES_6_torrents_visual.md`: **подтверждённых случаев, требующих новой разметки/JS, не найдено.** Два элемента, которые выглядели как вероятные кандидаты при поверхностном чтении экспорта, при сверке с исходниками оказались нативными:

- «раскрывающееся» поле поиска с текстом ввода — нативная кнопка `.filter--search` уже содержит скрытый (`class="hide"`) текстовый узел, который Lampa сама показывает по клику (`API_NOTES_5_torrents.md:205-206`); макет просто показывает уже открытое состояние.

**Один пункт остался неподтверждённым и требует живой проверки в Task 32 Step 1/3**: точка-индикатор «применён фильтр» на чипе «Фильтр» (экран 34). Ни в `API_NOTES_5`, ни в `API_NOTES_6` не нашлось описания класса/атрибута, который Filter выставляет при наличии применённых условий (документирован только `.selector`-toggle по наличию данных сортировки/фильтра вообще, `API_NOTES_5_torrents.md:226`, — не то же самое, что «есть активный выбор»). Если такого нативного признака нет — точку добавить только CSS нельзя: по инварианту §0.3 плана маркер-классы допускаются лишь на корнях `.selectbox`/`.modal`/активности/`body`, а не на отдельных чипах внутри панели, то есть потребовалось бы расширение архитектуры (новый JS-хук), а не просто CSS-правило.
