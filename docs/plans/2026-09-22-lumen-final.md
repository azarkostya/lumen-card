# Lumen Card — ФИНАЛЬНЫЙ план до готовой версии (2026-09-22)

> Этот документ заменяет очередь задач из планов фаз 5 и 6. Новых задач в него не добавлять: всё, что придёт после, — либо дефект (чинится в разделе A), либо откладывается за релиз (раздел D). Ведётся по `superpowers:subagent-driven-development`; ревью — одно на волну.

## Что значит «готово»

Версия считается готовой, когда одновременно верно всё:

1. На телевизоре пользователя (Philips 50PUS8057, режим движения `lite` — его выбор) нет ни одного известного дефекта уровня «важно»: кадр героя виден и меняется, логотип не подменяется на ходу, рулетка крутится, карточка длинного сериала открывается без провала, меню и фокус читаются.
2. По HUD с телевизора: главная в покое ≥ 55 fps, при листании ≥ 40, карточка «Дораэмон» без провала ниже 20.
3. Каждый пункт из четырёх отзывов пользователя (интервью 2026-09-21, отзыв 2026-09-21 вечером, скрины 2026-09-22 ×2) либо закрыт, либо явно отклонён им самим.
4. Все тесты зелёные, сборка актуальна, ES5 ok, планы и README отмечены.

Публикация в `main` — **решение пользователя**, план его не принимает.

## D. За релизом — не делать до «готово»

- **Task 65** виртуализация рядов главной — только если B2 покажет длинные задачи на шаге фокуса.
- Ряд широких плиток 16:9 вместо постеров — упирается в высоту и Task 65.
- Чипы настроения отдельным рядом — закрыто замером (не хватает 32 px), оба обхода не работают.
- Разбор композиции дизайнером по скринам — после релиза, с жёсткими рамками (без размытий, без прозрачных подложек, кегли ≥ 23 px, герой 2/3 неприкосновенен).
- «Как Apple TV» для меню и рулетки — там уже нейтральный фокус, отличий нет; не делать.
- Пороги автодетекта — не трогать: пользователь выбрал режим сам.
- **Долг, найденный при разборе A7: пол базового кегля Lampa 10.6 px модель раскладки не знает.** Lampa ставит `fontSize: Math.max(window.innerWidth / 84.17 * fs, 10.6)` (`vendor/lampa/app.min.js:31629-31640`) — **нижняя граница 10.6 px**, а `LC.util.lampaSizeK` (`src/10_util.js:136-157`), `screenEm()` (`src/30_css.js:692-700`) и `LAMPA_SIZES` в `test/css.test.mjs:2305` считают экран как `84.17 / k` без всякого пола. Пол включается при ширине окна меньше `10.6 × 84.17 / 0.9 = 991.3` CSS px, то есть **на всех окнах уже 991 px**, включая WebView телевизора (960). Следствие на «мельче» при 960 px: фактический кегль 10.6 вместо 10.264, экран содержит `960 / 10.6 = 90.57` базовых em, а модель берёт 93.52 — то есть **ширина экрана в em завышена примерно на 3.3 %**, и оба порога (узкая колонка `rowNarrowRatio`, потолок масштаба `rowScaleCap`) включаются **позже**, чем должны. Сейчас это ничего не ломает: все 72 клетки прогона раскладки в `test/css.test.mjs` укладываются в предел 532. **Но комментарий в `src/30_css.js:682-685` («84.17 при „обычном“, 93.52 при „мельче“ и 80.16 при „крупнее“») с приходом пола перестал быть правдой для „мельче“ на узких окнах**; та же неполная формулировка — в `src/10_util.js:138-144`. Код и комментарии этой правкой не трогались сознательно: долг зафиксирован здесь. Чего не проверял: сколько именно запаса остаётся у самой тяжёлой клетки «мельче» — число в модели не запинено, и своего замера я не делал.

- **Долг, найденный финальным ревью: ширина плитки хаба и карточки сетки считается без учёта размеров.** `TILE_EM`/`GCARD_EM` (`src/46_hub.js:86-93`) прибиты к `84.17` — без `lampaSizeK()` и без `uiScale()`, хотя ширина задана процентами контейнера, а `LC.util.emPx` домножает на масштаб плагина. Замеры исполнителя (2026-09-22): при «крупнее» и штатном масштабе расчёт завышен на **7.8 %** (5 % даёт `lampaSizeK`, 1.9 % — устаревший в формуле отступ: комментарий считает `2.81em` по краям, в CSS `EDGE = 3.51em`, `src/30_css.js:2102`); от `lumen_scale` расхождение доходит до **+25.6…+32.8 %** на «огромном» и до **−4…−9 %** на «мельче». **Ошибка двусторонняя, и в одну сторону она портит картинку:** при 1920 CSS px, DPR 1, Lampa «мельче» и `lumen_scale = 0.9` плитка хаба шириной 435 px получает с TMDB **w300 вместо w780** — видимое мыло. На целевых экранах (960 CSS px при DPR 2 и 1920 при DPR 1) ступень не расходится ни в одной из 12 проверенных клеток, поэтому релиз это не держит. Отдельной задачей.
- **Две клетки бюджета высоты стоят на самом краю — знать при любой правке геометрии ряда.** «Крупнее» + средний кадр + «огромный» масштаб: запас **0.031em ≈ 0.37 CSS px** (блок 23.889em при бюджете 23.920em). «Обычный» + крупный кадр + «огромный»: **0.046em**. Следующая правка ширины карточки, зазора или кегля подписи уронит их, и потолок `rowScaleCap` начнёт срезать масштаб уже и на среднем кадре — это будет не регрессия, а работа защиты, но заметят её как «масштаб перестал меняться». Обе клетки прогоняются в `test/css.test.mjs`, молча не пройдут.

## Почему было долго — и что меняется

Три причины, все настоящие:

1. **Каждое ревью находило 5–10 реальных дефектов.** Без него на телевизор приезжали бы пустые чекбоксы, обрезанные метки, невидимый фокус, подпись на кадре. Ревью остаётся, но одно на волну, не на задачу.
2. **Ложные посылки координатора** стоили примерно по раунду каждая: «TMDB со стенда недоступен», «в lite теряется заливка», выдуманная цитата Apple, «lite выставил автодетект». Правило записано в память: возражение исполнителя проверять замером, не настаивать.
3. **Стенд проверялся только пультом.** Дефект A1 жил с первой версии и не ловился ни одним тестом и ни одной живой проверкой — потому что стенд никогда не гоняли мышью. С волны A каждая живая проверка идёт в обоих режимах управления.

И одно организационное: **новых задач в этот план не добавляется.** Всё, что придёт после, — либо дефект в A, либо раздел D.
